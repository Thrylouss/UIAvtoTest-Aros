# aros-ui — UI автотесты (Java + Playwright + JUnit5)

Автоматизированные UI-тесты для маркетплейса Aros:
- витрина — https://staging.aros.uz
- админ-панель — https://staging-admin.aros.uz

Проект написан с расчётом на то, что вы новичок в Java — код нарочно
подробно закомментирован: не только ЧТО делает каждый класс, но и ПОЧЕМУ он
устроен именно так. Начните читать с этого README, потом открывайте файлы
в том порядке, в котором они здесь перечислены — так архитектура сложится
в голове по кусочкам, а не одной большой кучей.

## Стек и почему именно он

| Что | Выбор | Почему |
|---|---|---|
| Язык | Java 21 | Текущая LTS-версия |
| Сборка | Maven | Стандарт в Java-мире, `pom.xml` — аналог `requirements.txt` |
| Браузер | [Playwright](https://playwright.io/java/) | Автоожидание элементов "из коробки" — меньше нестабильных тестов, чем на Selenium |
| Test runner | JUnit 5 | Стандарт де-факто для новых Java-проектов |
| Отчёты | [Allure](https://allurereport.org/) | Читаемые HTML-отчёты со скриншотами и шагами теста |
| Паттерн | Page Object Model | Локаторы страниц отделены от самих тестов |

### Почему слои разделены именно так

**`config` → `playwrightsupport` → `base` → `pages` → `tests`** — каждый
следующий слой опирается на предыдущий и ничего не знает о том, что выше:

- **Тест** (`LoginTest`, `SearchTest`) описывает только бизнес-сценарий
  человеческим языком: "открыть форму, ввести данные, проверить результат".
  Ни одного CSS-селектора в тесте нет.
- **Page Object** (`SignInForm`, `HomePage`, `CatalogPage`, `ProductCard`)
  знает, ГДЕ на странице что находится, и предоставляет тесту простые
  методы уровня пользователя (`signInWithPassword(...)`,
  `searchBar().search(...)`). Если фронтенд поменяет вёрстку — чинить
  нужно только здесь.
- **`base`** — это переиспользуемый "клей": `BaseUiTest` даёт каждому
  тесту готовую страницу браузера и убирает её после, `BasePage` — общий
  родитель для Page Object'ов.
- **`playwrightsupport`** прячет детали именно Playwright API (Browser,
  BrowserContext, Page) — если завтра понадобится что-то тонко
  настроить (прокси, запись видео и т.п.), тест и Page Object'ы это не
  затронет.
- **`config`** — единственное место, где программа знает про `.env` и
  переменные окружения.

## Установка

1. Установите JDK 21+ и Maven (проверить: `java -version`, `mvn -version`).
2. Скопируйте `.env.example` в `.env` и заполните значения:
   ```bash
   cp .env.example .env
   ```
3. Установите браузер Chromium для Playwright (нужно один раз после
   клонирования репозитория — сам Playwright скачивается как обычная
   Java-библиотека через Maven, а вот РЕАЛЬНЫЙ браузер он держит отдельно
   и качает вот этой командой):
   ```bash
   mvn exec:java@install-browsers
   ```

## Запуск тестов — пошаговая инструкция

> Ничего «страшного» в запуске нет: тесты только ЧИТАЮТ сайт и добавляют/удаляют товары в корзине тестового
> пользователя. Заказы создают только тесты с тегом `creates-order` — их сейчас в проекте нет, они только
> для будущего (см. «Что осталось вам»).

**Один раз:** `cp .env.example .env`, заполните `TEST_USER_PHONE`/`TEST_USER_PASSWORD`, затем
`mvn exec:java@install-browsers` (скачивает Chromium).
Язык сайта задаёт `BASE_URL` (`https://staging.aros.uz/ru`; для `/en` тексты есть не везде — см. `i18n/Text.java`).

### Команды

```bash
mvn test                                        # ВСЕ тесты (≈15–20 минут)
mvn test -Dgroups=smoke                         # дымовые тесты — быстрая проверка, что сайт жив
mvn test -Dgroups=P1                            # только приоритет P1
mvn test -Dgroups='!known-defect'               # регресс: без проверок известных дефектов
mvn test -Dgroups=known-defect                  # только известные дефекты (они падают, пока не исправят)
mvn test -Dgroups=cart                          # один модуль (теги: auth header home catalog models search product
                                                #   cart checkout orders profile general l10n mobile)
mvn test -Dgroups=CART-006                      # один тест-кейс по ID из Excel
mvn test -Dgroups='CART-006 | AUTH-001'         # несколько кейсов
mvn test -Dtest=CartSummaryTest                 # один класс
mvn test -Dtest='CartSummaryTest#cartTotalsAreConsistent'   # один метод
mvn test -Dheadless=false                       # смотреть браузер вживую
```

Тесты «известных дефектов» (`@Tag("known-defect")`, ID вида `AUTH-X02`) специально ПАДАЮТ, пока дефект на сайте не
исправлен: они фиксируют найденные проблемы (опечатки, пустые экраны, «0 сум»). Для обычного регресса их исключайте.

### Что вы увидите

1. **В консоли** — по строке на каждый тест: `▶ старт`, `✔ ПРОШЁЛ` / `✘ УПАЛ` / `⏭ ПРОПУЩЕН`. Для упавшего —
   причина человеческим языком, URL страницы, **эндпоинты с ошибками** (метод, адрес, статус, начало запроса и ответа),
   ошибки консоли браузера и путь к скриншоту. В конце — итоговая таблица по модулям.
2. **HTML-отчёт** `target/qa-report/report.html` — те же данные, открывается в браузере (там же скриншоты).
3. `target/qa-report/results.json` — машиночитаемый результат (его читает `tools/sync_testcases.py`).
4. Если настроен Telegram — красивое сообщение в чат (см. ниже).
5. Allure-данные в `target/allure-results/` (опционально: `allure serve target/allure-results`).

## Запуск и отчёты через Telegram-бота

Бот работает на вашем компьютере: пока он запущен, вы шлёте ему команды в Telegram — он запускает тесты и присылает
отчёт: что прошло, что упало, **почему** (причина, эндпоинт и статус ответа, скриншот), и HTML-файл с подробностями.

**Настройка (один раз, ~3 минуты):**
1. В Telegram откройте `@BotFather` → `/newbot` → придумайте имя → получите **токен** вида `123456:ABC…`.
2. Напишите вашему новому боту любое сообщение (`/start`). Чтобы узнать свой chat id, откройте в браузере
   `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и найдите `"chat":{"id": 123456789`. (Для группы: добавьте бота в
   группу, напишите в ней, id группы будет отрицательным.)
3. В `.env` добавьте:
   ```
   TELEGRAM_BOT_TOKEN=123456:ABC...
   TELEGRAM_CHAT_ID=123456789          # можно несколько через запятую; бот слушает ТОЛЬКО эти чаты
   ```
4. Запустите бота и оставьте окно терминала открытым:
   ```bash
   mvn test-compile exec:java@telegram-bot
   ```
5. В Telegram: `/help`. Команды: `/smoke`, `/p1`, `/p2`, `/safe`, `/regress`, `/defects`, `/all`,
   `/module cart auth`, `/id AUTH-001 CART-006`, `/run P1 & cart`, `/status`, `/stop`, `/last`.

Отчёт придёт в Telegram и после ОБЫЧНОГО запуска `mvn test`, если в `.env` заданы токен и chat id.
Не хотите? `QA_NO_TELEGRAM=true mvn test`.

## Подбор локаторов: «зонд» страниц (PageProbe)

Когда нужно автоматизировать новый экран, не гадайте селекторы — посмотрите дерево элементов страницы:

```bash
# файл probe.txt:        goto:/ru/cart
#                        snap:-
mvn -q test-compile exec:java@probe -Dexec.args="--login --file probe.txt"
```
Команды файла: `goto:`, `click:`, `fill:селектор=значение`, `press:селектор=Enter`, `snap:` (дерево доступности),
`text:` (видимый текст), `eval:` (JS), `shot:` (скриншот в `target/probe/`), `wait:`. Опции: `--login`, `--state
target/auth/user.json` (старт с готовой сессией), `--mobile`, `--headed`, `--max N`. Полная справка — в javadoc `PageProbe`.

## Как устроены ID, теги и язык

- Каждый тест помечен ID кейса из Excel: `@Tag("CART-006")` + `@DisplayName("CART-006 · …")`, приоритетом (`@P1/@P2/@P3`),
  при необходимости `@Smoke`, `@CreatesOrder`; на классе — тег модуля (`@Tag("cart")`). Дополнительные проверки, которых не
  было в Excel, имеют ID с буквой X: `AUTH-X02`.
- Тексты на экране берите из `i18n/Text.java`, а не пишите строкой в локаторе — тогда тест переживёт смену языка.
- Тесты «вошедшего» наследуйте от `AuthenticatedUiTest`: вход делается один раз за прогон (`AuthSession`), корзина
  очищается до и после.
- После добавления тестов: `python3 -m venv .venv && .venv/bin/pip install openpyxl`, затем
  `.venv/bin/python tools/sync_testcases.py --dry-run` (посмотреть) и без `--dry-run` (записать статусы в Excel;
  перед записью делается резервная копия в `docs/test-cases/backup/`). С результатами:
  `--results target/qa-report/results.json`.

## Тесты авторизации на витрине (`LoginTest`)

| Тест | Что проверяет |
|---|---|
| `successfulLoginWithValidCredentials` | happy path: валидные телефон+пароль → toast «успех» и шапка сайта показывает, что пользователь вошёл |
| `loginFailsWithWrongPassword` | неверный пароль → входа не происходит |
| `loginFailsWithInvalidPhoneFormat` (×4, параметризованный) | короткий/длинный/нечисловой номер |
| `loginFailsWithEmptyPassword` / `loginFailsWithEmptyPhoneNumber` | обязательные поля не дают войти пустыми |
| `passwordIsMaskedByDefaultAndToggleRevealsIt` | UI: маскирование пароля и переключатель-"глазик" |
| `switchingBetweenPhoneAndPasswordLoginModes` | UI: переключение режимов входа |

## Тесты поиска товаров (`SearchTest`)

| Тест | Что проверяет |
|---|---|
| `searchingByRealProductNameFindsThatProduct` | поиск по названию реального товара находит именно его (сверка по pvId) |
| `searchResultsAreRelevantToQuery` | все результаты выдачи релевантны ключевому слову запроса |
| `searchingUnknownTermShowsEmptyState` | заведомо несуществующий запрос → состояние "нет товаров" |
| `openingSearchResultNavigatesToMatchingProduct` | клик по результату поиска открывает именно этот товар |

**Ключевая идея этого модуля — динамичность.** Ни в одном тесте нет
захардкоженного названия товара или ID. Вместо этого каждый тест сначала
берёт `homePage.firstProductCard()` — ЛЮБОЙ товар, который реально
существует на сайте прямо сейчас, — и строит запрос из его собственных
данных (`ProductCard.slugKeyword()` / `slugPhrase()` / `pvId()`, см.
подробные комментарии в `ProductCard.java`). Каталог живой: товары
заканчиваются и переименовываются, и тест, который сам находит себе
объект для проверки, не ломается из-за этого просто так.

Все тесты (и логина, и поиска) реально прогонялись против
`https://staging.aros.uz` десятки раз, в том числе несколько прогонов
подряд для проверки на нестабильность. По пути нашлось и было исправлено
несколько настоящих багов автоматизации:

- **Гонка с SPA-роутингом.** Переходы между страницами здесь — это
  клиентский роутинг (React), а не полная перезагрузка: URL браузера и
  содержимое страницы обновляются не мгновенно после клика/сабмита. Если
  проверять результат сразу же, можно поймать промежуточный кадр и
  ошибочно решить, что "выдача не та" или "переход не случился". Решение
  везде одно и то же: явный `page.waitForURL(...)` перед тем, как
  доверять содержимому страницы (см. `SearchBar.search(...)` и
  `ProductPage.assertOpenedProductWithPvId(...)`).
- **Ненадёжная кнопка отправки поиска.** Клик по кнопке-лупе периодически
  ничего не делал (гонка с внутренним ре-рендером React прямо во время
  набора текста) — заменили на нажатие Enter в самом поле, которое
  сработало стабильно во всех проверках (см. `SearchBar.java`).
- **Маскированное поле телефона** (уже встречалось в `LoginTest`) — та же
  причина, то же решение: `fill()` вместо посимвольного ввода.
- **Поиск случайной строкой не гарантирует пустую выдачу.** Если строка
  содержит настоящие английские слова (например "product"), поиск сайта
  иногда возвращает общую выдачу вместо "нет товаров" — похоже на нечёткое
  совпадение по отдельным словам. Решение — генерировать запрос без
  словарных слов, только из букв и цифр (см. комментарий в `SearchTest`).

## Тесты корзины (`CartTest`)

| Тест | Что проверяет |
|---|---|
| `addingProductShowsStepperOnCardAndUpdatesCartBadge` | сразу после добавления карточка показывает степпер количества, бейдж в шапке — 1 |
| `addedProductAppearsInCartPageWithCorrectQuantity` | добавленный товар реально виден на странице `/cart` с верным количеством |
| `increasingQuantityInCartUpdatesItemsCount` | "+" в корзине увеличивает количество и общий счётчик товаров |
| `decreasingQuantityToZeroRemovesItemAndEmptiesCart` | "-" от количества 1 удаляет товар и опустошает корзину (так ведёт себя сайт) |
| `removingOneItemKeepsOthersInCart` | удаление одного товара (через чекбоксы + "Delete") не трогает остальные |

Тот же принцип, что и в `SearchTest`: товар для добавления в корзину
берётся динамически (`homePage.firstProductCard()` /
`homePage.productCards()`), ни одного захардкоженного названия или ID.
Корзина на этом сайте гостевая — тесты не логинятся, добавление в
корзину работает и без авторизации.

Этот модуль дался труднее остальных — на живом стенде обнаружилось
СЕМЬ разных, накладывающихся друг на друга причин нестабильности, и все
исправлены:

- **Кнопка "Добавить в корзину" — не то, чем кажется.** У товаров с
  датой ближайшей поставки эта кнопка визуально подписана "Tomorrow at
  15:00"/"Today at 15:00" вместо иконки корзины, но функционально это
  ОДНА И ТА ЖЕ кнопка — просто с другим текстом (см. `ProductCard`).
- **Поле количества нулевого размера.** `<input type="number">`,
  который хранит текущее количество на карточке/в корзине, реально
  существует и содержит верное значение, но занимает `0×0` пикселей —
  видимое число рисуется как-то иначе. Playwright справедливо считает
  такой элемент невидимым, и ждать его видимости — вечный таймаут.
  Значение читается как обычно (`inputValue()`/`hasValue()` не требуют
  видимости), но ждать и кликать по нему нельзя — дожидаемся вместо
  этого исчезновения кнопки "Добавить в корзину" (см. `ProductCard.addToCart()`).
- **Гонка с рендером степпера.** Сразу после клика по "Добавить в
  корзину" карточка на мгновение оказывается "ни тем, ни тем" — старая
  кнопка уже пропала, новый степпер ещё не отрисовался.
- **Уведомление "Product added to cart!" оставляет невидимый след.**
  Даже после того как всплывающее уведомление скрывается, его собственная
  ссылка на товар какое-то время остаётся в DOM (просто невидимая) — и
  без фильтра `:visible` на локаторах карточек товаров она попадала в
  общий список и сдвигала индексы `nth(0)/nth(1)`, из-за чего "второй
  товар" на самом деле оказывался тем же первым (см. `HomePage`/`CatalogPage`).
- **Быстрые повторные действия иногда ловят rate-limit.** Если менять
  количество или чекбоксы подряд без паузы, сайт иногда отвечает
  toastify-тостом с ошибкой, чей фиксированный контейнер перекрывает
  часть шапки — добавлена небольшая пауза между такими действиями (см.
  `CartLineItem`/`CartPage`).
- **"Delete" — не настоящая кнопка.** Это `<p>Delete</p>` внутри `<div>`
  с обработчиком клика, без `role="button"` и без тега `<button>` —
  `getByRole(BUTTON, "Delete")` никогда её не находил. Локатор — по
  тексту напрямую (см. `CartPage`).
- **Сводка в корзине считает только ОТМЕЧЕННОЕ.** "Products count" и
  "Total" в правой панели — это сумма по товарам, у которых стоит
  галочка, а не по всей корзине. Раз для точечного удаления одного
  товара нужно СНИМАТЬ галочки с остальных, после удаления их приходится
  заново отмечать — иначе следующая проверка сводки ложно видит "0 Items"
  на совершенно реальных оставшихся товарах (см. `CartPage.removeItem`).

## Тесты админ-панели (`AdminLoginTest`)

Тесты не пропускаются: `ADMIN_USERNAME`/`ADMIN_PASSWORD` заполнены в
`.env` и оба теста реально проходят против `https://staging-admin.aros.uz`.
Если креды пока не заполнены — `@BeforeEach`-проверка аккуратно
**пропускает** оба теста (жёлтый статус, не красный) вместо падения.
Стоит уточнить локаторы в `AdminDashboardPage` — сейчас там временная,
максимально общая проверка (см. TODO-комментарий в файле); более глубокое
покрытие самой админки — материал для отдельного следующего модуля.

## Как добавить новый тест (шпаргалка для новичка)

1. Если тест про новую страницу — создайте для неё Page Object в
   `pages/...`, унаследовав от `BasePage` (см. `HomePage.java` как пример).
2. Локаторы ищите через `page.getByRole(...)` / `getByPlaceholder(...)` и
   похожие — НЕ через сгенерированные CSS-классы (обычно вида
   `mui-xxxxx` или `css-xxxxx` — они меняются при каждой пересборке
   фронтенда).
3. Тестовый класс кладите в `tests/...`, наследуя от `BaseUiTest` — поле
   `page` (открытая вкладка браузера) будет готово к использованию в
   каждом `@Test`-методе.
4. Сам тест должен читаться как рассказ: `homePage.open()`,
   `form.signInWithPassword(...)`, `homePage.assertUserIsLoggedIn()` — а
   не как список кликов по селекторам.
5. **Избегайте хардкода реальных данных** (конкретных ID товаров, имён,
   текстов) — там, где это возможно, доставайте их динамически со
   страницы (см. `ProductCard` и `SearchTest` как образец). Хардкод
   ломается сам по себе, когда каталог/данные меняются, даже если сам
   функционал работает исправно.
6. Если действие ведёт к переходу на другую "страницу" внутри SPA —
   добавьте `page.waitForURL(...)` перед тем, как проверять содержимое
   новой страницы (см. раздел про гонку с SPA-роутингом выше). Это самый
   частый источник ложных падений в этом проекте.

## Что автоматизировано, а что осталось вам

Автоматизировано ≈ 84 кейса из Excel + 7 дополнительных проверок (лист «Доп. проверки (авто)»). Остальное —
сознательно: причина каждого пропущенного кейса записана в колонке M листа «Тест-кейсы». Главное:

- **Создание заказов** (CHK-014/015/021…), отмена/смена оплаты, редактирование профиля и адресов — меняют данные;
  такие тесты нужно писать с `@CreatesOrder` и запускать только осознанно (`/all` в боте).
- **Нужна админка или второй аккаунт** (заказы-интеграции, долг, баллы, роли) — сначала нужен API админки для подготовки данных.
- **OTP по SMS** — отложено по плану.
- **«Избранное»** — на staging не нашлась страница (`/ru/favorites` → 404): уточните у разработчиков.
- **Мобильное нижнее меню и оформление** — нужна разведка через `PageProbe --mobile`.

## Известные ограничения / что дальше

- Восстановление пароля, регистрация и вход по одноразовому коду через
  телефон — пока не покрыты. `SignInForm` уже содержит локаторы
  `forgotPasswordButton()` / `signUpButton()` для этого следующего шага.
- Точный текст toast об ошибке (`Toast.expectError()`) есть в коде, но ни
  разу не проверялся против конкретной формулировки сайта — используйте с
  осторожностью, пока не сверите текст вручную.
- `CatalogPage` пока не покрывает фильтры (цена/производитель/категория) и
  сортировку — только сам факт наличия/отсутствия результатов и их
  релевантность.
- Оформление заказа (`Checkout`) и более глубокое покрытие страницы
  товара (выбор цвета/комплектации, отзывы) — следующие модули;
  `ProductCard`/`ProductPage`/`CartPage` уже дают для них основу.
- Точная сумма/скидка в корзине (`Products price`, `Discount`) не
  проверяется — только количество товаров и их состав. Формат валюты
  ("30 000 sum" с неразрывными пробелами) достаточно специфичен, чтобы
  делать это отдельным, аккуратным шагом.
- В консоли при запуске тестов выводится длинный `RuntimeException` от
  AspectJ ("Unsupported class file major version..."). Это шумный, но
  БЕЗОБИДНЫЙ предупреждение о несовместимости конкретно вашей версии JDK
  (27, очень свежая) с загрузчиком аспектов Allure — на сами тесты и на
  корректность отчёта (шаги/скриншоты) он не влияет, это было явно
  проверено. Если раздражает — запустите тесты на JDK 21.

## CI

`.github/workflows/ui-tests.yml` — прогоняет `mvn test` на каждый PR и push
в `main`, публикует Allure-отчёт как артефакт сборки. Чтобы тесты на
витрину заработали в CI, добавьте в Settings → Secrets репозитория:
`BASE_URL`, `TEST_USER_PHONE`, `TEST_USER_PASSWORD`, `TEST_USER_WRONG_PASSWORD`,
а для тестов админки — `ADMIN_BASE_URL`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`.
